ATT（App Tracking Transparency）

iOS 14.5+ 必須のトラッキング許可ダイアログ制御仕様

v1.3 機能ID: RS-FEAT-ATT

概要

Apple の App Tracking Transparency（ATT）フレームワークに基づき、広告ネットワークによる IDFA（広告識別子）利用前にユーザーの許可を求める。 許可状況に応じて Unity LevelPlay がパーソナライズ広告と非パーソナライズ広告を切り替える。

2026-08-20: 広告基盤を AppLovin MAX から Unity LevelPlay へ移行した （AdMob 恒久停止後に移った AppLovin の publisher アカウント承認が下りなかったため）。 2026-08-23 の ITPassportMaster 移行をもって全8アプリが LevelPlay で統一されている。 詳細は 広告制御 を参照。
2026-08-23 設計変更: ATT ダイアログの表示条件を AdEnvironment.isAdDeliveryAvailable から AdEnvironment.shouldRequestTracking へ分離した。 広告の「配信」は App Store 版のみに限定したままで、ATT ダイアログの「表示」は審査ビルドでも行う。 理由は下記「ATT ダイアログの表示条件」を参照。

ATT ダイアログの表示条件（2026-08-23 設計変更）

問題: ATT ダイアログの表示を AdEnvironment.isAdDeliveryAvailable でガードしていた。 この値は isProduction（レシートが sandboxReceipt でないこと）を条件に含む。 App Store の審査は TestFlight と同じ sandbox 環境で実行されるため、 審査担当者の手元では ATT ダイアログが原理的に表示されない状態になっていた。
実害: 2026-08-22、姉妹アプリ CHROMATIC 1.4.0(7) が iPadOS 26.6 での審査において Guideline 2.1 - Information Needed でリジェクトされた。

対策：配信可否と ATT 表示可否の分離

広告を「配信してよいか」と、ATT ダイアログを「表示してよいか」は別の条件であると整理し、判定を2本立てにした。

/// 広告の「配信」は App Store 版のみ（isAdDeliveryAvailable）に限定するが、
/// ATT ダイアログの「表示」は審査ビルドでも行わなければならない。
static var shouldRequestTracking: Bool { !appKey.isEmpty }
判定条件用途
isAdDeliveryAvailable!appKey.isEmpty && isProduction広告の SDK 初期化・ロード・表示（App Store 配信版のみ）
shouldRequestTracking!appKey.isEmptyATT ダイアログの表示（TestFlight・審査ビルドを含む）
環境ATT ダイアログ広告の配信
App Store 配信版表示する配信する
審査（sandbox）／ TestFlight表示する配信しない
DEBUG / シミュレーター表示する（App Key 設定済みの場合）配信しない
App Key 未設定表示しない配信しない
App Key 未設定＝広告を一切出さない版では ATT ダイアログを表示しない。 これにより「広告がないのにトラッキング許可を求める」ことを禁じる Guideline 5.1.2 の懸念も同時に満たす。
本アプリへの適用状況: 未適用（2026-08-23 時点）
本セクションは「あるべき設計」として記載している。 2026-08-23 に shouldRequestTracking を実装したのは StudyStopwatch / RoutineReel / WorkoutDiary と、先行して修正済みの CHROMATIC であり、 RankingStadium のコードにはまだ適用していない。
RankingStadium は現在 1.0.2 が審査中であり、CHROMATIC と同じ理由でリジェクトされる可能性がある。 次回ビルドで AdEnvironment.shouldRequestTracking を導入し、 ContentView の ATT 要求ガードを差し替えること。

プロンプト表示タイミング

ContentView の authenticated 遷移（ホーム表示後）で ATTrackingManager.requestTrackingAuthorization を1回要求する。 ただし要求するのは AdEnvironment.shouldRequestTracking（App Key 設定済み）の場合のみ。 未適用 RankingStadium のコードは現在も isAdDeliveryAvailable でガードしている。
条件動作
AdEnvironment.shouldRequestTracking が false（App Key 未設定）プロンプトを表示しない（広告を一切出さないため）
sandbox 環境（審査 / TestFlight）プロンプトを表示する（審査担当者が確認できるようにするため）
アプリが active のときプロンプトを表示する
アプリが inactive のときプロンプトを表示しない（OSが無視するため）
scenePhase が .active に復帰したとき未許諾（.notDetermined）であれば再試行して取り逃しを防ぐ
すでに許可 / 拒否済み再プロンプトは表示しない（OS 制御）

処理フロー

sequenceDiagram participant App as ContentView participant Env as AdEnvironment participant ATT as ATTrackingManager participant LP as Unity LevelPlay App->>App: authenticated 遷移 (ホーム表示) App->>Env: shouldRequestTracking alt App Key 未設定（広告を一切出さない版） Env-->>App: false Note over App,LP: ATT プロンプトを表示しない else App Key 設定済み（App Store 配信版 / 審査 / TestFlight） Env-->>App: true App->>App: scenePhase == .active を確認 App->>ATT: requestTrackingAuthorization() ATT-->>App: status (.authorized / .denied / .restricted / .notDetermined) alt status == .authorized App->>LP: IDFA 利用 (パーソナライズ広告) else status != .authorized App->>LP: IDFA 非利用 (非パーソナライズ広告) end Note over App,LP: 広告の配信自体は isAdDeliveryAvailable が true
（App Store 配信版）の場合に限る end Note over App: scenePhase 復帰時に .notDetermined なら再試行

NSUserTrackingUsageDescription

Info.plist に設定するユーザー向け説明文（App Store 審査で具体性を求められる）:
あなたの興味・関心に合った広告を表示するため、広告識別子（IDFA）の利用許可をお願いしています。許可しない場合も、アプリの全機能をご利用いただけます。

Unity LevelPlay との連携

ATT ステータス広告配信の動作
.authorizedIDFA を利用したパーソナライズ広告を配信
.denied / .restrictedIDFA を利用しない非パーソナライズ広告を配信
.notDetermined非パーソナライズ広告（プロンプト未回答の間）
LevelPlay SDK と Unity Ads アダプタは ATT の許可状況を OS から検出して IDFA 利用 / 非パーソナライズを切り替える。 アプリ側でフラグを手動設定する必要はない。

プライバシーマニフェスト（PrivacyInfo.xcprivacy）の方針

正解は NSPrivacyTracking: false ＋ NSPrivacyTrackingDomains キーごと削除。 誤って NSPrivacyTracking を true に戻したり、NSPrivacyTrackingDomains を復活させたりしないこと。
キー設定理由
NSPrivacyTracking false true かつ NSPrivacyTrackingDomains が空だと ITMS-91064 でリジェクトされる。2026-08-20 に3本同時被弾し、うち2本が DailyTips と RankingStadium だった
NSPrivacyTrackingDomains キーごと削除 これは申告項目ではなく実行時のブロックリスト。載せたドメインは ATT 非許可時に OS が通信ごと遮断する
Unity Ads は広告配信とトラッキングで同じドメインを使う。 そのため NSPrivacyTrackingDomains に載せると、ATT を拒否したユーザーには広告が1本も出なくなる。

トラッキングの申告は App Store Connect の App Privacy 側で行う。プライバシーマニフェストで申告するものではない。

ビジネスルール

  • ATT プロンプトは App Key が設定されている場合に表示する（shouldRequestTracking）。審査・TestFlight でも表示する
  • 広告の配信は App Store 配信版のみ（isAdDeliveryAvailable）。ATT の表示条件とは分離する
  • App Key 未設定＝広告を一切出さない版では ATT プロンプトを表示しない（Guideline 5.1.2）
  • ATT プロンプトはアプリ起動中に1度のみ表示（iOS OS 制御）
  • 許可・拒否にかかわらず、アプリの全機能を利用可能とする
  • 設定アプリから後から変更可能であることを設定画面で案内する
  • プロンプトは active 状態のときのみ要求し、inactive 時は要求しない
